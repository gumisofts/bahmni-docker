# Operating a Bahmni Standard site

Everything below is done with the scripts in this directory. They are idempotent: re-running one
never breaks a working site. All of them run from `bahmni-standard/` and read the server's `.env`.

| Script | Purpose |
|---|---|
| `install.sh` | Fresh installation on an Ubuntu server (on-premises or cloud). |
| `bootstrap-site.sh` | Apply all post-start configuration (passwords, Odoo shop/order types, PACS wiring, Metabase setup, DB auth for the atomfeed console). Safe to re-run. |
| `update.sh` | Upgrade the site to the latest commit while keeping the server `.env`. |
| `backup_to_cloud.sh` | Nightly encrypted off-site backup (databases + data volumes) to the gumisofts backup server. |
| `restore_from_cloud.sh` | Disaster recovery: rebuild a site from the off-site backup. |
| `add_pacs_procedure_codes.py`, `odoo_bootstrap.py` | Helpers called by `bootstrap-site.sh`. |

`.env` in git holds only the stock Bahmni defaults. The server's `.env` is generated by `install.sh`,
holds every secret of the site and is marked `skip-worktree` so `git pull` never touches it.
**Back it up to a password manager: without it a restore is impossible.**

## 1. Enrol the hospital on the backup server (once, on the cloud server)

```bash
sudo backup-server/setup.sh --public-url https://hms.gumisofts.com/restic   # first time only
sudo backup-server/add_site.sh hospitala
```

`add_site.sh` prints the three `BACKUP_*` values for the hospital. Backups are append-only: a
hospital can add snapshots but never delete or overwrite them. Retention (7 daily, 4 weekly,
12 monthly) and integrity checks run on the cloud server (`backup-server/prune.sh`, daily cron);
`sudo backup-server/prune.sh --status` shows when each site last backed up.

## 2. Install on the hospital server

Requirements: Ubuntu 22.04/24.04, 8 CPU, 32 GB RAM, 500 GB SSD, static IP, a UPS. Internet is
only needed during installation (or use `--load-images` with a bundle made by
`docker compose config --images | xargs docker save -o bahmni-images.tar`).

```bash
git clone https://github.com/gumisofts/bahmni-docker.git && cd bahmni-docker/bahmni-standard
sudo scripts/install.sh --site-name hospitala --hostname hms.hospitala.local \
     --backup-repo '<BACKUP_REPOSITORY from add_site.sh>' --backup-password '<BACKUP_PASSWORD>'
```

The installer asks for one admin password (used for the OpenMRS, OpenELIS, Odoo, dcm4chee and
Metabase admin logins), generates all other secrets, installs Docker if needed, pulls the images,
starts OpenMRS first (so its stock passwords are replaced before the other services connect),
starts everything else, runs `bootstrap-site.sh`, takes the first backup and installs the nightly
cron. It ends with a summary (also saved to `install-summary.txt`).

After installation:

1. DNS on the hospital network: `hms.hospitala.local` and `erp-hms.hospitala.local` -> server IP.
2. X-ray/CT/ultrasound machines: send to server IP, port `11112`, AE title `DCM4CHEE`.
3. In the EMR: Admin -> create locations, wards, beds, providers and users.
4. Prove the backup works: `scripts/restore_from_cloud.sh --list` shows the first snapshot.

Behind an existing reverse proxy (like the cloud server) use `--behind-proxy`, which binds to
`127.0.0.1:8080/8443` instead of `0.0.0.0:80/443`.

## 3. Day to day

```bash
scripts/bootstrap-site.sh              # re-apply configuration / rotate passwords changed in .env
scripts/backup_to_cloud.sh --check     # last snapshots in the repository
scripts/backup_to_cloud.sh             # manual backup now
tail backup-artifacts/backup.log       # nightly results (one "BACKUP OK" line per night)
scripts/update.sh                      # upgrade to the latest commit of this repository
docker compose ps                      # service health
```

`update.sh` lists any new settings introduced by the update; review them in `.env` and then run
`scripts/bootstrap-site.sh`. `bootstrap-site.sh` never writes a stock template password into a running
site: a stage whose credentials are still at the template value fails with a message instead.

Upgrading a server that was installed before these scripts existed (the script is fetched first
because the checkout does not have it yet):

```bash
cd ~/bahmni-docker && git fetch -q && git show origin/master:bahmni-standard/scripts/update.sh > /tmp/update.sh \
  && COMPOSE_DIR=$PWD/bahmni-standard bash /tmp/update.sh --no-restart
```

Then set the new `*_ADMIN_PASSWORD` / `ODOO_MASTER_PASSWORD` keys in `.env` to the passwords the site
already uses, `docker compose up -d`, `scripts/bootstrap-site.sh`.

## 4. Disaster recovery

On a repaired server, a replacement server, or a per-hospital project on the cloud:

```bash
git clone https://github.com/gumisofts/bahmni-docker.git && cd bahmni-docker/bahmni-standard
cp /your/password-manager/hospitala.env .env      # the site's original .env (same secrets!)
docker compose up -d openmrsdb openmrs proxy       # any start is fine; restore replaces the data
scripts/restore_from_cloud.sh --list
scripts/restore_from_cloud.sh                      # or --snapshot <id>
```

The restore stops the applications, drops and reloads every database from the dumps, overwrites the
data volumes from the snapshot, starts everything, re-runs `bootstrap-site.sh` and prints a
comparison of row counts (patients, lab patients, sale orders, studies) between the backup manifest
and the restored databases.

If the `.env` was lost, install fresh with `install.sh` **using the same admin password** and then
copy the `*_DB_PASSWORD` / `MYSQL_ROOT_PASSWORD` / `PACS_DB_ROOT_PASSWORD` values into the new
`.env` from the backup of the original `.env` - the database dumps are self-contained but the
containers must be started with the credentials the dumps expect.

Expected recovery objectives: data loss at most one night (RPO ~24 h), recovery in a few hours (RTO).
Test a restore into a scratch project at least quarterly:
`COMPOSE_PROJECT_NAME=drtest` in a copy of the directory with `--behind-proxy` ports.

## What bootstrap-site.sh fixes (for the curious)

Stock Bahmni images leave these unconfigured; every one of them was found by hand on the cloud
demo before being scripted:

- OpenMRS: `superman/Admin123`, `admin/Admin123`, `reports-user/Admin123` and other demo accounts;
  `pacsquery.pacsConfig` empty (radiology viewer 501).
- Odoo: no Sales Shop / order types (EMR orders silently dropped), `proxy_mode` off (login loop
  behind HTTPS), database manager open, default `admin` password.
- pacs-integration: no modality / order type rows (orders never reach the worklist); radiology
  concepts without `PACS Procedure Code` mappings ("Missing concept source for order").
- OpenELIS and dcm4chee default admin passwords; Metabase first-run race.
- MySQL 8 / PostgreSQL 16 authentication too new for the atomfeed console's JDBC drivers.
